# Vogantra: مراجعة الكور وخطة التنفيذ

تاريخ المراجعة: 2026-09-07. نسخة المقارنة: `edc6d4059aab9a48d7cfeeb1ef7871155a181a23` من main.

## نطاق الدليل وحدوده

هذه مراجعة مباشرة لواجهات دفتره المذكورة أدناه ومقارنة بكود Vogantra وملفات ترحيله. لم تُنشأ معاملات أو تُعدّل إعدادات في دفتره. وجود عنصر في القائمة لا يثبت صحة تشغيله. لا تمثل المراجعة اعتمادًا محاسبيًا أو اختبارًا كاملًا للبرنامجين.

الوصول إلى قاعدة Vogantra عبر موصل Supabase أعاد `You do not have permission to perform this action` عند طلب قراءة سياسات الجداول. لم نحاول تجاوز الرفض. لذلك تعريفات SQL المذكورة دليل من المستودع، وليست تأكيدًا لحالة قاعدة الإنتاج الحالية. التغييرات في هذه الدفعة لا تتضمن SQL ولا إعادة ترحيل أرصدة.

## تصميم المرحلة التالية: الأدوار والأقسام

- أقسام المؤسسة هي تبعية تنظيمية، لا تمنح صلاحيات بحسب الاسم.
- دور مخصص ومجموعة صلاحيات داخل organization_id؛ ربط الموظف بالدور داخل العضوية نفسها.
- كتالوج إجراءات ثابت ومعروف للتطبيق، مع تسميات عربية؛ فصل العرض/الإنشاء/التعديل/الحذف/الإلغاء/التصدير/الاعتماد/التنفيذ.
- نطاق البيانات مستقل لكل منحة: own/team/branch/organization. تعريف ownership وteam لكل مورد قبل استخدامه في RLS.
- لا دمج نطاقات الفرع والفريق بترتيب رقمي؛ لكل منهما مجموعة بيانات مختلفة.
- الاستثناء الصريح بالمنع يسبق المنح من الأدوار؛ صلاحيات المالك المحمية وإدارة المنصة تُحدد بصورة منفصلة.
- فحص تفعيل الشركة للميديول، الباقة، العضوية، الإجراء، النطاق، شرط الاعتماد في الخادم.
- لا كشف حقول التكلفة والربح بمجرد السماح بقراءة bookings؛ تحتاج projections/RPCs محمية ومراجعة التصدير والتقارير.
- جدول تعيينات ومفاتيح مركبة تمنع ربط دور/قسم/فرع من شركة أخرى، مع فحص العضوية النشطة.
- النقل من السياسة الحالية يتطلب معاينة فروق الصلاحيات قبل تفعيله لكل شركة، وإمكانية الرجوع.

## خطوات التنفيذ المرتبة

1. إكمال المقارنة على الإعدادات والقوالب والتشغيل، واستعادة وصول قاعدة البيانات المصرح به.
2. إنشاء بيئة اختبار معزولة وتثبيت مصفوفة RLS والـRPCs الحالية؛ لا بيانات مالية حقيقية في الاختبارات.
3. تنفيذ دور/صلاحية/نطاق لكل شركة مع شاشة تحرير ونسخ ومعاينة، ثم نقل كل نقطة إنفاذ مستخدمة فعليًا.
4. ربط الأقسام والفرق والميديولات بالباقات وتسليم العمل؛ التحقق من اعتماد الميديولات على بعضها.
5. توجيه الحسابات مركزيًا مع اختبارات القيد والمستند والتقرير وإقفال الفترة ومنع التكرار.
6. دورة الرحلة متعددة الخدمات والموردين والعملات، ثم التعديل والإلغاء والاسترداد والعمولة.
7. القوالب والاستيراد وتجربة الموبايل وتهيئة الاشتراك وقياس التحويل الفعلي.

## بوابات القبول

- شركتان وأدوار مختلفة لنفس المستخدم؛ منع الوصول عبر تغيير ID أو استدعاء API مباشر أو تصدير.
- نتائج العرض والتصدير والـRPC لا تتجاوز نطاق الموظف؛ inactive membership مرفوض.
- منع الموظف من رفع صلاحياته أو اعتماد ما لا يسمح به الدور؛ حد الاعتماد يُطبق بعملة وسياسة محددتين.
- مستند واحد ينتج أثرًا واحدًا؛ إعادة المحاولة لا تضاعف الإيراد أو التحصيل أو السداد.
- تعديل/إلغاء خدمة بفواتير مدفوعة لا يعيد كتابة التاريخ بصمت؛ مستند تصحيح وأثر قابل للتتبع.
- لكل عملة: مستند → قيد → أستاذ → ميزان؛ افتتاحي + حركة = ختامي، ومنع الخلط بين النقدية والربحية.
- اختبار إغلاق الفترة ورفض الترحيل إليها، ثم إعادة الفتح بصلاحية وسجل واضحين.

## التحقق من هذه الدفعة

- `npm run test:company-core`: اختبارات سلوكية لترتيب الشجرة والبحث والأيتام والدورات وروابط الشركات المختلفة، واختبار provider الفعلي بردود عضوية متأخرة/مرفوضة.
- `npm run build`: نجح بناء Vite؛ هذا ليس دليلًا على سلامة أنواع المشروع كله أو قاعدة البيانات.
- ESLint للملفات المعدلة: بلا أخطاء؛ بقيت تحذيرات hooks/fast-refresh السابقة في OrganizationContext.
- RLS وSQL والدورة المالية الحية: محجوبة بعد رفض صلاحية موصل Supabase؛ لم تُختبر ولم تُعدّل.
- عرض الشاشات المعدلة في متصفح التطبيق: لم يكتمل بعد؛ مراجعة دفتره لا تُحسب اختبارًا لواجهة Vogantra.

مرجع حماية قاعدة البيانات: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). فحوص الواجهة دفاع إضافي وليست بديلًا عن سياسات الخادم.
